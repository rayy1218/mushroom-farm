## Frozen interfaces

- **Wire format:** spec §2 exactly (both D and S implement it independently; no shared code).
- **HTTP:** spec §4.1 room fields (`relayAddress`, `acAddress` in every room object), §4.3 routes, §4.4 JSON.
- **Device store API** (for the lead's e2e test): `sensors.add({ address, kind: 'relay'|'ac' })`, `sensors.update(address, patch)` where relay patch = `{ stuck: [b,b,b,b] }`, `{ dead: [...] }`, `{ answering }` (coils change only through Modbus), AC patch = `{ roomT, error, refuse, answering }`; `sensors.get(address)` returns `{ address, kind, coils:[4], stuck:[4], dead:[4], running:[4], answering }` or `{ address, kind, power, mode, setpoint, fan, roomT, error, refuse, answering }` with `mode`/`fan` as numbers (codes of §2) and `setpoint` in °C. Running needs the 2 s spin-up: make the spin-up time an option of `startDevice({ spinUpMs = 2000 })` / `createSensors({ spinUpMs })` so tests use 0.
- **Server modules:** `createModbusClient` gains `readBits(unit, fn /*1|2*/, start, qty) → Promise<boolean[]>`, `writeCoil(unit, address, on) → Promise<void>`, `writeRegisters(unit, start, values) → Promise<void>` (same queue, timeouts, errors, reply validation incl. echo check). `createPoller` also polls machines (spec §4.2) and exposes `machineState(roomId)` (the in-memory last-2 polls); the API reads it. A `createMachines({ db, client, poller, now })` module (or functions in api.js) handles commands and builds the §4.4 object.
